# Character Registration

At startup, CivReg reads the CAD database sync configuration. When character database sync is disabled, players use `/civreg` to open the community's live CAD character template (`7`) and create a character. Linked players send their CAD community user ID; unlinked players send their FiveM identifier so the backend can associate the character after they use `/link`.

When both database sync and its character mapping are enabled, CivReg switches to database mode. It adds a nullable `sonoran_mugshot MEDIUMTEXT` column to the standard QBCore `players` table or ESX `users` table on every resource start. CivReg captures the portrait automatically after a QBCore or ESX character finishes spawning. QBCore captures wait for the active `citizenid`, a stable spawned ped, and a `qb-clothing` skin signal for the player ped when that resource is running; signals for character preview peds are ignored. On a fresh login with Illenium or FiveM Appearance, capture waits for a real appearance change and then a stability window. If the provider never applies an appearance, capture times out instead of saving a placeholder portrait. Running `/civreg` only explains that no manual registration is needed, and selecting a character in CAD does not trigger a framework database write. It does not create an API character in this mode. Configure CAD DB Sync to map `sonoran_mugshot` to the character template's image field.

When `frameworksupport` is enabled, supported QBCore or ESX identity values are pre-filled. If the CAD template uses custom Field Mapping IDs, update `autofillFieldIds` in `configuration/civreg_config.lua`.

Image fields are clearly marked as selfie controls in API mode. During either manual or automatic capture, CivReg makes a local copy of the player's ped, removes masks, hats, glasses, ear props, and neck accessories from that copy, and leaves the player's appearance untouched. The copy must match the selected skin before capture; it is deleted after conversion or failure. A portrait is rejected if the live player's ped or appearance changes during capture. Captured portraits are submitted directly to CAD as base64 PNG or JPEG data (including the `data:image/...;base64,` prefix). Database mode stores the same data URL in `sonoran_mugshot`. Each portrait is validated against `maxSelfieBytes`; the default decoded size limit is 1 MiB. With SonoranCAD debug logging enabled, client logs prefixed `[civreg portrait]` show skin signals and capture decisions without including image data.

New portraits do not require a public image URL or a local image file. The old `selfieBaseUrl` option is ignored. Existing URL-based records keep their original references, so the `civreg` file route remains available for previously saved portraits. Preserve those files and their public route while existing records use them.

Automatic portraits now require ten continuous seconds of a stable, fully spawned appearance. This duration is a fixed internal constant in `core/headshots.lua` and is not configurable. The readiness wait allows up to 60 seconds for a slow character load. Existing clothing/provider checks still apply. Client capture rechecks the ready character, ped, and appearance when the server request arrives, and rejects changes during conversion. The server also rejects an upload if the active framework character changed. A rejected capture leaves the existing database portrait untouched.

Every completed character-selection capture and manual selfie creates a new clone and registers a fresh headshot. Conversion uses a unique texture URL for every request, following the [Cfx headshot example](https://github.com/citizenfx/natives/blob/master/PED/RegisterPedheadshot.md), so a recycled texture name does not reuse the previous browser response. Late or duplicate conversion callbacks cannot overwrite a newer image or release its headshot. In-flight duplicate requests are still coalesced; completed portraits are never used as a capture cache.

For loading issues, enable SonoranCAD debug mode before selecting the character and collect the client's F8 output plus the server console output. `[civreg portrait]` logs show the detected appearance resources, character and ped, visibility/collision/fade state, clothing signals, applied props, stability resets, wait duration, capture result, and database save. Readiness progress is logged at most once every five seconds. `[civreg headshot]` logs show fresh native registrations, conversion request IDs, completion, and ignored stale callbacks. Image contents and capture authorization tokens are not logged. These diagnostics help identify custom clothing loads that happen after the normal framework events; a stability timer alone cannot certify a custom provider's completion.

Run the standalone regression tests from the repository root with `lua .codex/tests/civreg_registration_spec.lua`, `lua .codex/tests/civreg_database_sync_spec.lua`, `lua .codex/tests/civreg_framework_selection_spec.lua`, `lua .codex/tests/civreg_portrait_capture_spec.lua`, `lua .codex/tests/headshots_spec.lua`, and `lua .codex/tests/linking_account_uuid_spec.lua` (Lua 5.4 or newer). They stub the FiveM, CAD, and SQL boundaries and do not connect to a live CAD community or database.
